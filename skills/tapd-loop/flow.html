tapd-loop 链路

从读到配置，到一张卡在工位上跑完、合进主树、写回 TAPD。每张卡片都能点开，看这个节点的输入、输出、内部具体做了什么。

主干分成两段：跑卡（A–E，一条命令、一棵树、一张卡）和合入（F，工位交上来的提交怎么进主树）。G 是人从看板介入的地方，H 收尾。

外循环 · node 进程 内循环 · pi 子进程 TAPD · tapd-cli 仓库 · git 看板 · HTTP + 按钮 出口 = 离开主流程

点任意卡片看内部细节。关闭用 Esc、点空白处，或右上角按钮。

  1. 启动：一次性准备，和卡片无关

  2. 外循环解析参数，叠出最终配置

    • 五层覆盖：内置默认 → ~/.tapd-loop/config.json → <git-common-dir>/tapd-loop.json → --config 文件 → 命令行参数
    • 仓库级配置住在 .git/ 里，所以工作区永远干净；同一仓库的所有 worktree 共用这一份（配置只有一份，工位只是不同的检出目录）
    • 仓库根的老位置 .tapd-loop.json 仍能读但会告警，--migrate-config 搬进 .git/
    • 没有 task.assignee 直接报错（--fetch / --show / --retry 除外）
    结果 cfg 对象，附 cfg.sources 记录每层文件路径与是否命中

  3. 外循环开通道、查仓库、建运行目录、塞无人值守标记

    • createTapd()：workspace、状态 key 表、四个机器标签名、checkDependencies / doneStatuses
    • 必须是 git 仓库；工作区脏就拒跑（--dry-run / --migrate-config / --allow-dirty 除外）
    • 补上 TAPD_LOOP=1 / LUBAN_NO_PAUSE=1 / GIT_TERMINAL_PROMPT=0：项目钩子看到它们就不弹交互，否则整批会冻死在收尾那步
    • runDir = ~/.tapd-loop/runs/run-<时间戳>/，之后所有事件按行追加到 progress.jsonl，同时旁路写 ~/.tapd-loop/index.jsonl

  4. 看板拉起常驻进程，拿到一个固定地址

    start-board.mjs 用 detached 子进程起 serve.mjs，默认绑 0.0.0.0:7317，地址写进 ~/.tapd-loop/board.json。已在跑就复用。出网时 /api/* 要密钥，打出来的 url 自带 ?k=。每次跑 loop 都会先确认看板在跑，--no-board 可关。

    起不来只打一条日志，不影响干活，只是没页面可看

  5. 外循环四个不跑内循环的入口

    • --list 只看队列：就绪卡 + 被状态 / 机器标签 / 前置挡住的 rejected 与原因
    • --show <id> 只读地看一张卡能不能接：不认领、不评论、不建 runDir
    • --fetch <id> 只把一张卡的标题 / 详情 / 评论 / 图片抓到 ~/.tapd-loop/cards/<id>
    • --retry <id> 只碰标签：撕 afk-*、加回 ready-for-agent，把失败的卡放回队列
    为什么单列 看板的「查看这张 / 重跑」和聊天里贴链接走的都是这几条，它们不动 TAPD 状态、不动代码，所以不需要一整批的护栏

  6. 外循环两个提前退出的口

    • --dry-run：打印 sources、cfg、队列，然后退出。不建 runDir、不动 TAPD
    • push 闸门：push.enabled 但 verify 为空 → 启动即报错。等一张卡跑完二十分钟才告诉你，代价太大
  7. 每一轮：先看还要不要跑，再挑一张卡

  8. 外循环四个停止条件

    • <git-dir>/tapd-loop-stop 存在（每棵树独立，停一棵不影响其他）
    • maxTasks 到量 · maxFailures 连败
    • 同一处错误连挂两张不同的卡（stopOnSameFailure）：多半是门禁 / 环境坏了，再跑只是烧 token
    • 自动放回队列的那次失败不算 maxFailures（它还没报废）；一旦 blocked 立刻停整批

  9. TAPD拉队列，挑第一张能做的

    • story list owner=<处理人> label=ready-for-agent，过滤掉带任何机器标签的
    • 状态要在 statuses 里（默认开发中 / 实现中）；前置依赖没完成的也算接不了
    • partitionTagged() 把「能接」与「接不了 + 原因」分开，后者进 --list 的 rejected，不静默跳过
    • 依赖来自 story time-relations（tapd-cli ≥ 1.16），按 doneStatuses 或状态名判完成，按进程缓存 60 秒
    • 排序：优先级升序，再按 id 字典序

  10. 外循环进入 runCard()，再查一次状态和依赖

    列表到开工之间可能被人改过，所以在跑任何前置之前先确认状态还在范围内、前置还都完成——preflight 要跑 sync / afterSync，代价不小。

    状态已变 / 前置没完成记 skipped，回去拿下一张，不算失败
  11. 开工前置：顺序不能换，先清场、再同步、最后取基线

  12. 仓库salvage：把上一批留下的脏工作区存走再清干净

    • 被 taskkill /F、断电、关终端杀掉的那批不会走失败收尾，工作区里留着半截改动
    • 那些东西既挡 pull --rebase（于是整张卡干在陈旧基线上），又会被本卡的 git add -A 一起提交
    • 先存成 tapd-loop-orphan/<卡片id>（<runDir>/<id>/orphan.patch 也落一份），再清干净
    • 存不进去就整批停（blocked）：宁可不跑，也不让别人的 diff 混进来
    关掉 run.salvageDirty: false

  13. 仓库开工前同步：git pull --rebase

    • 必须在取基线之前：rebase 会改写历史，基线若取在它前面，失败回滚会把刚拉到的上游 commit 一起抹掉
    • 工作区停在半截 rebase / merge / cherry-pick 时，先按标记文件清干净再继续
    • 网络类失败重试 sync.retries 次
    • 多工位并行建议开 sync.strict：同步没成功就不在陈旧基线上开工（不算 fatal，不牵连别的工位）
    冲突或未跟踪文件挡住上游同名文件 → rebase --abort，这张卡记 blocked，整批停
    只是没 upstream / detached / 已跟踪文件脏 → 记一条跳过日志，照常开工

  14. 仓库afterSync 护栏：修好机器人看不见的脏状态

    • DigitDoor 填 bash Tools/GitHooks/Luban/after-update.sh；无条件每张卡跑一次，不是「sync 真动过才跑」
    • 理由：脏导出不只由本循环造成。人在外面 rebase / cherry-pick / reset 都不触发 post-merge / post-checkout，而导表守卫挂在那两个钩子上
    • 跑完比对 git status：护栏自己留下新改动也不行，那些会被 add -A 算进本卡提交
    护栏失败或留下脏改动 → 记 blocked，整批停。导出是旧的，开了工也白做

  15. 仓库记下基线 baseline = git HEAD

    这张卡后面所有的「有没有改动」判定和失败回滚都以它为锚。到这里仓库历史才可以被认为稳定。

  16. TAPD占住这张卡：加 afk-claimed

    多份拷贝并行时靠它互斥，谁先加谁拿到。写标签一律回读校验，多值字段用竖线分隔。

    占不到（已有别的机器标签 / 状态被改回）→ 记 skipped，换下一张

  17. TAPD抓工单，落成本地素材

    • 读正文 + 全部评论，HTML 转纯文本
    • 正文里的 /tfl/ 内嵌图：attachment get-image 换签名地址再下载，最多 30 张，正文改写成相对路径
    • attempt = 正文里 [tapd-loop] 失败 出现次数 + 1，用来告诉内循环这是第几次
    产出 card.md（人看） · card.json（机器看） · images/
    读取失败 → 进失败收尾（先存档再回滚）

  18. 外循环拼 brief：只讲这张卡和边界

    • 写「工作目录、这张卡是什么、边界、怎么算完成、最后输出什么」
    • 不写技能正文，也不写「去读 SKILL.md」。技能正文由下一步 pi 直接注入
    • 边界原文：只改本卡范围 · 不要执行任何 git 命令 · 不要问人 · 不留调试代码 · 结尾给 RESULT: 与 COMMIT: 两行
    产出 brief.md
  19. 交给内循环：从这一步开始模型介入

  20. 内循环起一个 pi 子进程，技能正文由 pi 自己读进去

    • --append-system-prompt <SKILL.md 路径>：给路径时 pi 读的是文件内容，正文确定性地进系统提示
    • --skill <yogioo-mode>：只登记 name/description/path，正文进不来
    • @brief.md：brief 展开成用户消息；--session-id 捕下来，验证失败时用同一个会话续跑
    • stdout 全量落 events.jsonl，stderr 落 pi.log；超时或卡死都 taskkill /T /F 连子树一起杀
    • turnStallSec 看的是「进程活着但什么都不发生」，和总时长 timeoutSec 分开
    这里越过了进程边界：两个进程、两个模型上下文，外循环看不到里面怎么想

  21. 内循环自己把活跑完，外循环不干预

    • 按已注入的指令选 playbook（Bug fix / Feature / Investigation …），把步骤抄成清单
    • 需要并行就把活拆给 agent-tools subagent 的只读 arm
    • 改代码，用 Unity MCP 复现与验证，跑相关 EditMode 用例
    • 不碰 git：只在工作区留下改动，结尾输出 RESULT / COMMIT
    产出 工作区改动 + events.jsonl（可能几十 MB，含每一次工具调用）
  22. 判定、自愈与发布：能救的先救，救不回来的再判死

  23. 外循环四道硬闸，只认客观信号

    1. 卡住不动（turnStallSec 内没有任何新输出）
    2. 超时（timeoutSec）
    3. 事件流里有 agent_settled 且没 aborted
    4. git.changedSince(baseline)：工作区脏或 HEAD 动了
    任一条不过 → 失败收尾（先存档再回滚，见 E5），不是当场丢

  24. 外循环跑 verify，并分清「代码坏了」和「环境没起来」

    • 退出码 0 通过；非 0 再分三类：代码问题 / 环境问题（verifyEnvExitCodes）/ 门禁没验成（verifyGateExitCodes）
    • 环境码命中：先睡 verifyEnvRetryDelaySec 再重跑，最多 verifyEnvRetries 轮，任一过就继续走成功路径
    • 仍不过才落回失败，但原因写「这不是代码问题」，人不用去查业务代码
    • 标签语义不变：环境失败仍然是失败，只是先自己再试几次

  25. 外循环verifyRepair：把失败输出回灌给同一个会话

    • 只在代码类失败上触发；环境问题与门禁没验不会把 AI 拉回来改业务代码
    • 每轮把 verify.log 末尾 150 行写进 repair-<n>/prompt.md，用同一个 --session-id 续跑
    • 两道护栏：动了 forbidPaths（默认 .workflow/，改尺子不算本事）立即失败；这一轮没动任何文件也立即停
    • 默认关（maxRounds 2）：一轮就是一个完整 turn，token 与时间都要涨

  26. 外循环门禁自己没验成（exit 3）与失败签名

    • 「说好要跑测试，却一个用例都没跑到」是门禁坏了，不是这张卡写错了：verifyGateExitCodes 命中不重试，原因写清
    • 2026-10-31 之前这种情况是假绿：验证脚本只写一条注就 exit 0，没被验证过的卡被当成验收通过
    • 失败签名 = verify.log 第一行 ERR，去掉行号 / 参数 / 工单号，交给批次判 stopOnSameFailure

  27. 外循环失败收尾：先存档，再决定是重跑还是打住

    • 没提交就失败 → 改动原样存成 tapd-loop-failed/<卡片id>，再 reset --hard 回基线（工作区干净、活还在）
    • 已经提交但推不上去 → 提交挪到 tapd-loop-unpushed/<卡片id>，当前分支退回父节点
    • attempt = 卡上「[tapd-loop] 失败」评论条数 + 1；没到 maxCardAttempts（默认 2）只撕 afk-claimed、保留 ready、不打 afk-failed，下一轮自动再来
    • 额度用完才摘 ready-for-agent + 打 afk-failed，评论写原因、分支名和 --retry 的用法
    • 自动放回那次不计 maxFailures，但签名照样参与 stopOnSameFailure
    看改动 git diff <基线>..tapd-loop-failed/<卡片id>；<runDir>/<id>/diff.txt 也有一份

  28. 仓库提交

    • 工作区有改动才 git add -A + commit；没有改动就不提交（不硬造空提交）
    • message 取内循环那行 COMMIT: <type>:<7位工单号> <描述>，工单号必须是卡片 id 后 7 位，对不上用卡片标题兜底
    • 不带 AI 署名，不写 19 位全 id
    • diff.txt 在推送之前就落盘：之后一旦 rebase，旧 commit 可能变得不可达

  29. 仓库再同步一次，然后 git push（或留在工位等合入）

    • 卡跑了十几到几十分钟，期间别人可能又推了，所以推之前必须再造一次 pull --rebase
    • 最多 push.retries + 1 轮；网络抖和 rejected / fetch first 算可重试，分支保护不算
    • 永不 --force。共享分支上强推等于删别人的提交
    • 工位跑卡时 push 一般关着：提交留在工位本地，等主树 collect.mjs 合入（见 F1）
    同步冲突 / 远端拒绝 → 不丢活也不留在当前分支：提交挪到 tapd-loop-unpushed/<卡片id>，当前分支退回父节点，进失败收尾
    verify 为空（且没写 allowUnverified） → 启动时就被拦了，走不到这里

  30. TAPD换标签，发验收评论（writeback.mjs）

    • 回写抽成一个模块：loop 的成功 / 失败收尾和看板的合入补写都调它，不再各写一套
    • 撕 afk-claimed，加 afk-delivered（多值字段，写完回读校验）
    • 评论 = 抬头 + 结论前 2000 字（按句子边界截）+ 提交信息 + 看板证据链接
    • 没推上去就不报 sha：工位流程只写「本地已提交、未推远端；合入主树并推送后会补发最终提交号」
    • 推成功才写 提交：<sha10>（已推送 origin/branch）；想看本地 sha 配 run.writeBack.showLocalCommit
    评论写失败只记 warning，不回滚——代码已经提交了
  31. 合入：工位 → 主树（并行拓扑的另一半）

  32. 仓库collect.mjs <工位分支>：pick → 导表 → verify → push → 回写

    • 工位跑卡时提交只活在工位本地，合入是另一条命令：人点「合入 N」，或自动合入按时触发
    • 硬门槛：主树干净 + 没冲突 + 这棵树的 Unity 端点在线 + 没有别的主树任务在跑；一次只合一个工位（只有一块 Unity）
    • pick 前先 assertMergeableRef：tapd-loop-failed/* 与 tapd-loop-orphan/* 直接拒，unpushed/* 只拦自动
    • pick / 导表之前先探端点，不在线就 exit 3，不「pick 完了才在 verify 那步炸」
    • 成功后回写 TAPD：只报合入后的新 sha，工位原始 sha 已经不代表任何能查到的东西

  33. 仓库冲突：表格先三方叠，剩下的才起 agent 解

    • collect 冲突时 exit 2 并保留现场，看板看到 2 就自动起解冲突（按 digitdoor-git-pull-rebase），不用人再点一次
    • 表格先按显示值三方叠（xlsx-cell-diff merge，git show :1:/:2:/:3: 取三方版本）：两边改的是不同格就直接合掉、git add 后继续
    • 只有同一格两边都改、或 sheet / 行 / 列增删才算真冲突，拦下来等人，退避拉满 30 分钟
    • 「表格冲突必须人工合」已经不成立了

  34. 仓库合入成功之后：工位归位、待合入按内容判

    • cherry-pick 换了 SHA，分支留着 git cherry 会永远报 +，卡片一直挂「有 N 个提交待合入」而点进去只跑出一句空提交
    • 合入 status done 时板子把工位 reset --hard origin/<target>（工位有未提交改动、或停在存档分支则跳过）
    • 待合入计数：git cherry + 按内容再判一次（它改过的路径在主树里已经一样 → 不算待合入）
    • cherry-pick is now empty 不再 abort 整批：--skip 跳过后继续，最后列出跳过的 sha；整批都空就直接收工
  35. 看板：人怎么介入这套循环

  36. 看板面板 = CLI 的按钮版，取卡 / 合入 / 推送都只调脚本

    • 顶上：工作目录 / 处理人 / 本批最多 / 允许脏 / 只演练；查看队列 · 接单开跑 · 只跑这张
    • 自动化开关：定时接单 · 主树自动验证并推送 · 主树自动合入工位提交（默认关，它往共享分支写东西）
    • 右上：统计弹窗 · 重启看板（端口与链接不变）· 停看板（停进程，不是停批次）
    • 红框条「需要人处理 N 张」：本地索引判 + 拿 TAPD 现状核实，每行带「重跑」/「已处理」
    • 页面没有第二套实现：跑批 spawn loop.mjs，合入 / 推送调 collect.mjs

  37. 看板工位卡片：接活、终止、一次一批

    • 每棵工位一张卡：在跑 / 空闲 / 脏、待合入几个、卡片标题；勾选框「接活」= station.paused，只影响派卡，不碰手上那张
    • 在跑工位上的「停掉这一批」/ 卡片弹窗的「■ 终止」= taskkill /T /F 杀进程树，唯一能停掉手上那张卡的东西（停止文件对工位批次读不到）
    • 杀之前服务端复核 pid 真是 loop.mjs（Windows 会复用 pid）；判活看 progress.jsonl 里的 pid，网页和 CLI 不会在同一仓库撞车
    • 终止不走收尾：工作区留半截改动（下一批 salvage 存成 orphan 分支）、TAPD 上留 afk-claimed（要 --retry）
    • 「接这张」先问「在哪棵树上跑」：工位在前、主树在最后且再确认；服务端对主树还要 allowMain，否则 409

  38. 看板追溯与统计：index.jsonl 旁路索引

    • 链路本来散在 runs/、progress.jsonl、board-control.json、board-batches/ 四处且没有关联键；现在每个关键节点往 ~/.tapd-loop/index.jsonl 追加一行（t / kind / runId / card / sha / station）
    • trace.mjs --card / --day / --sha / --rebuild / --stats：一张卡的所有尝试、某天几批几张、某提交属于哪张卡
    • 索引是旁路：写失败不影响干活，删掉能用 --rebuild 回填（merged 历史补不回来）
    • 统计口径：一张卡 = 一个 TAPD 工单，多跑一次算一次重试；一次通过率 = 首次就成功的工单占比；耗时只算成功尝试的 p50 / p90
    • 不做 token / 成本统计、不做按仓库过滤（要解析每卡 31MB 的事件流，代价远超收益）
  39. 收尾：跳出循环，把这一轮汇总

  40. 外循环写报告，打一行 JSON 摘要就退

    • 退出原因：stop-file / blocked / same-failure / max-tasks / max-failures / empty-queue
    • report.md：每张卡一行状态与说明

一张卡的八种结局

结局什么时候改动去哪了整批
done四道硬闸 + verify 全过，提交、推送、回写都成已在远端继续
done（未推）同上，但工位流程 push 关着在工位本地提交，等 collect 合入继续
skipped状态不在范围、占不到卡、前置依赖没完成无改动继续
blocked同步冲突、afterSync 红 / 留脏、salvage 存不下无改动停
failed（还有额度）卡死 / 超时 / 没 settled / 无改动 / verify 红存到 tapd-loop-failed/<id>，工作区回滚自动放回队列，不计数
failed（额度用完）同一张卡第 maxCardAttempts 次失败同上，存档分支保留计数
failed（提交后）推送前同步冲突、远端拒绝、分支保护挑到 tapd-loop-unpushed/<id>计数
failed（环境 / 门禁）Unity 端点不在、门禁一个用例都没跑到（exit 3）存档分支保留，但原因写明「不是代码问题」计数

两条分界线：①「提交有没有发生」——提交之后回滚等于把这张卡的活扔掉，所以换成挑到具名分支；②「还准不准再试一次」——第一次失败先自动放回队列，到次数才摘 ready-for-agent。

并行拓扑：谁在写什么

主树工位（worktree）看板
干什么接单跑卡 + 把工位的提交合进来并推送接单跑卡，push 关着，提交只留在本地派单、看进度、给按钮
写共享分支collect 合入后 push不写远端不直接写
怎么停停止文件（下一张之前生效）终止 = 杀进程树；「接活」开关只停派卡重启 / 停看板只停服务，不影响已 detach 的批次
一次几批1 批每棵工位 1 批，多棵并行判活看 progress.jsonl 的 pid，网页与 CLI 不会撞车
Unity合入时用这块端点（所以一次只合一个）各自一块，跑卡时用派单前检查工位可用性

工位上的卡跑完不会被直接推上去：它先进「待合入」，由主树的 collect.mjs cherry-pick 进来、导表、verify、push，再用合入后的 sha 回写 TAPD。

两个循环的分工

外循环（tapd-loop）内循环（yogioo-mode）
是什么一个 node 脚本，跑完就退一个 pi 会话，被外循环 spawn
管什么取卡、同步、判定、提交、推送 / 合入、回写想清楚、改代码、自己验证
模型参与没有全程
git 写操作sync / commit / push / rollback / 存档分支禁止
TAPD 写操作标签、评论禁止
怎么算成功进程正常 + 有改动 + verify 过（+ 推得上去 / 合得进去）自己说 RESULT，但不算数
读这张图的方式　蓝色 = 确定性代码，紫色 = 模型在跑，橙色 = 动 TAPD 数据，绿色 = 动 git 历史，灰色 = 人按的按钮。 紫色那段是唯一不可控的，所以判定全压在它之后的蓝色步骤上，且只认进程、git、verify 三个客观信号；救不回来的失败也不丢活，先进存档分支再回滚。
